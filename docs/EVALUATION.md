# Evaluation

This project separates **component metrics** (how good is the detector? the
OCR?) from **system metrics** (how often does the whole pipeline produce a
correct, actionable detection?). Both are produced by tooling that runs the real
model on real data — nothing in this file is hand-written; the numbers below
were generated by the commands shown and can be regenerated.

> The trained weights and the dataset are gitignored, so these commands are run
> locally by the owner. CI stays model-free (see [TESTING.md](TESTING.md)).

## 1. Detector — `evaluate_model.py`

Authoritative per-class precision/recall + mAP (via Ultralytics `val()`) plus a
second error-analysis pass that matches predictions to ground truth for class
confusions, representative FP/FN, and a confidence-vs-correctness separation.

```bash
python3 evaluate_model.py \
    --model runs/detect/traffic_model-2/weights/best.pt \
    --data master_traffic_violation_dataset/data.yaml \
    --split val --benchmark
```

### Measured results — `traffic-4class@1.0.0`, val split

*Model:* `runs/detect/traffic_model-2/weights/best.pt` (YOLOv8n, 3.0 M params,
8.1 GFLOPs) · *device:* Apple M4 (MPS) · *conf=0.25, iou=0.5, imgsz=640* ·
generated 2026-09-11.

**Headline:** mAP@50 **0.697**, mAP@50-95 **0.502**, mean precision 0.783,
mean recall 0.740.

| class | precision | recall | mAP@50 | mAP@50-95 |
|-------|----------:|-------:|-------:|----------:|
| `Plate` | 0.941 | 0.780 | 0.811 | 0.428 |
| `WithHelmet` | 0.420 | 0.630 | 0.443 | 0.361 |
| `WithoutHelmet` | 0.848 | 0.696 | 0.688 | 0.565 |
| `TripleRiding` | 0.922 | 0.854 | 0.846 | 0.654 |

**Confidence vs correctness** (error-analysis pass, 383 images): mean confidence
0.809 when correct vs 0.561 when wrong — a separation of **+0.248**. The score
is *discriminative* (higher when right) but is **not** a calibrated probability;
see the confidence note below.

### Honest reading of these numbers

* **The detector is the weakest link, and `WithHelmet` is the weakest class**
  (P=0.42, mAP@50=0.44). Two compounding reasons: (a) only **27** `WithHelmet`
  instances in the val split, so the metric is high-variance; (b) the model
  genuinely confuses helmeted/un-helmeted heads (16 `WithoutHelmet`→`WithHelmet`
  and 4 the other way in the analysed set). This is *why* the runtime never
  reports `no_helmet` on a raw box — it requires the contradiction check plus a
  multi-frame temporal streak before a fine is raised.
* `TripleRiding` and `Plate` localisation are strong (mAP@50 0.85 / 0.81).
* `Plate`'s low mAP@50-95 (0.43) reflects loose box tightness, which is fine —
  OCR only needs a plate crop, not a pixel-perfect box.
* These are **component** numbers on a small, same-pool val set. They are not a
  claim about field accuracy; see the leakage/imbalance caveats in
  [DATASET.md](DATASET.md).

## 2. OCR — `evaluate_ocr.py`

Evaluates plate OCR against a labelled CSV (`image_path,plate`) and reports
exact-match, character accuracy, normalised-match, mean edit distance, invalid
(structure-failing) rate, and a confidence-vs-correctness split — optionally
broken down by a `condition` column (clean/blur/angle/lowlight/small/occluded).
It also compares preprocessing variants so a change is kept only if it measures
better. See [OCR section below](#ocr-preprocessing) and `evaluate_ocr.py --help`.

```bash
python3 evaluate_ocr.py --labels ocr_eval.csv --compare-preprocess
```

*No labelled OCR set ships with the repo, so no OCR numbers are asserted here.*
Provide `ocr_eval.csv` to produce them; the temporal OCR voting used at runtime
(`modules/plate_recognizer.py`) is separately unit-tested.

## 3. Whole system — end-to-end evaluation

Raw detector mAP is not the same question as *"how often does the complete
pipeline (detect → track → associate → OCR → temporal confirm → confidence →
violation → evidence) emit a correct, attributable fine?"* The end-to-end
evaluation framework (`modules/system_eval.py`, added in the CV-engineering
upgrade) answers that on deterministic synthetic scenarios and reports
system-level TP / FP / FN, wrong-vehicle and wrong-plate attribution, and
duplicate fines — deliberately separate from the YOLO numbers above. See its
module docstring and tests for the scenario definitions.

## Confidence is a score, not a probability

The pipeline treats `confidence` as an ordering score, never a calibrated
probability, and the UI/labels reflect that. The measured +0.248 separation
above says the score is *useful for ranking* review queues, not that "0.8 means
80% correct". Calibration (reliability curve, ECE, Brier) is an optional,
labelled-data experiment; until it is run and passes, no probability
interpretation is exposed. Speed is likewise labelled an **estimate**, not radar
truth (see [ARCHITECTURE.md](ARCHITECTURE.md) / speed validation).

## Regenerating everything

The detector report lands in `reports/` as both Markdown and JSON; the JSON is
what feeds the model manifest's `metrics` block
([MODEL_VERSIONING.md](MODEL_VERSIONING.md)). Re-running the command at the top
of this file overwrites both.
